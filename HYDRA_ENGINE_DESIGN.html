1. Purpose

Hydra Engine is a universal staffing decision system for Amazon Sort Centers. It models a facility as a directed graph of process paths, computes everything provable with deterministic code, and uses an AI layer as an interpreter of operator-authored rules to handle the judgment that cannot be hardcoded.

The engine does not claim to be smarter than the operator. The operator is the domain expert; the engine's job is to hold the facility's live state and math perfectly, and to apply the operator's intent — expressed as natural-language rules — to situations the operator could not enumerate in advance.

2. Problem Statement

Every sort center makes staffing decisions 10+ times per shift — allocating finite headcount across process paths to maximize throughput. Today this is done by:

  • Manual estimation using static spreadsheet planners (built once pre-shift, stale within 20 minutes)
  • Gut-feel adjustments as conditions change
  • Inconsistent quality across shifts, sites, and experience levels

The result: suboptimal TPH, missed CPTs, overstaffed areas coexisting with bottlenecks, and no systematic way to carry good judgment across shifts, people, and 100+ sort centers.

Two failure modes bound the design:

  1. Pure hardcoding is too rigid. No fixed algorithm can anticipate every site quirk, edge case, or tradeoff an experienced operator makes on instinct.
  2. Pure AI is unsafe and unauditable. An LLM allowed to "just optimize the floor" will hallucinate numbers, violate physical constraints, and produce decisions nobody can trace or trust.

Hydra Engine resolves this by drawing a hard line between the two: code owns everything provable; AI owns only the interpretation of the operator's rules, and is never allowed to override math.

4. Product Requirements

4.1 Functional Requirements

  • FR-1: Accept any sort center's process topology as a directed graph
  • FR-2: Ingest live data (trailers, WIP, headcount, rates) from existing APIs
  • FR-3: Produce a constraint-valid baseline HC allocation with zero AI involvement
  • FR-4: Accept operator-authored rules (natural language) scoped to nodes and to the site
  • FR-5: Use AI to interpret those rules against live state and propose adjustments to the baseline
  • FR-6: Re-validate every AI-proposed adjustment against hard constraints before accepting it
  • FR-7: Respect all operational constraints (min/max HC, grouping rules, flow physics, headcount conservation)
  • FR-8: Provide phased timeline showing when staffing should shift as conditions change
  • FR-9: Report projected throughput (transient and steady-state), current bottleneck, and risks with time-to-threshold
  • FR-10: Explain every decision, tracing each adjustment back to the specific rule that caused it
  • FR-11: Work for any NASC regardless of equipment type, process paths, or volume mix

4.2 Non-Functional Requirements

  • NFR-1: Produce a recommendation within 60 seconds of request
  • NFR-2: No site-specific code — all variation handled through graph definition + operator rules
  • NFR-3: Operate from a userscript (Tampermonkey) with no infrastructure dependencies beyond a lightweight AI server
  • NFR-4: Safety is never AI-dependent — the system must produce a valid plan with zero rules and zero AI availability
  • NFR-5: Every AI proposal is validated by code before it can affect output
  • NFR-6: Degrade gracefully when data is unavailable (flag missing inputs, compute with what's available)
  • NFR-7: Every decision is auditable — traceable to a rule, a constraint, or deterministic math

5. Architecture

5.1 Core Philosophy: The Operator Is the Expert, AI Is the Interpreter

Hydra Engine is built on one principle:

Code owns everything provable. The operator owns judgment. AI is the operator's interpreter — it translates human intent into concrete moves, bounded by math it is not permitted to violate.

This is a deliberate reframing. The AI is not an optimizer and not a domain expert. It is a translation layer that takes:

  • fuzzy human intent ("keep jam break covered when recirc risk is climbing"), and
  • hard deterministic state (the live graph, the constraint-valid baseline),

and produces a concrete, bounded proposal ("move 2 HC into jam_break") that code then re-validates before anything reaches the operator.

Three consequences follow:

  1. The AI can never hallucinate a number into production, because it never does arithmetic and every proposal is re-checked by the deterministic validator.
  2. The AI is additive, never load-bearing for safety. With zero rules or zero AI availability, the deterministic baseline is still a complete, valid plan.
  3. Every decision is auditable. An adjustment traces to a specific rule on a specific node; a rejection traces to a specific constraint.

5.4 What Changed From v1.0

v1.0 treated the AI as a single holistic "reasoning layer" that received the whole graph and returned a full plan. That conflated two very different jobs (deciding vs. explaining) into one unauditable call, and it left the operator's own judgment with no first-class home in the system.

v2.0 makes three structural changes:

  1. Operator rules are a first-class data type (Section 6.5), scoped to nodes and to the site. They are the primary mechanism for flexibility.
  2. AI decision-making is split from AI explanation. Decisions happen as small, scoped, per-rule proposals that code validates (Section 9). Explanation is one holistic narration call over the already-final plan (Section 10).
  3. The deterministic baseline is a hard requirement, not a fallback. The system must always be able to produce a complete valid plan with zero rules and no AI.

6.5 Operator Rules (First-Class)

Operator rules are the flexibility mechanism. They are natural-language statements of intent authored by the person running the floor. They exist at two scopes:

Node-scoped rules (node.ai_rules[]) — apply when reasoning about one node's allocation:

{
  "id": "rule_jam_recirc",
  "scope": "node",
  "node_id": "jam_break",
  "text": "Keep jam break staffed to at least 2 when mezz WIP is trending toward the recirc threshold, even if it means pulling from induct.",
  "priority": "high",
  "enabled": true
}

Site-scoped rules (graph.site_rules[]) — global tiebreakers used during reconciliation when nodes compete for finite headcount:

{
  "id": "rule_cpt_first",
  "scope": "site",
  "text": "When two areas compete for the last available people, protect CPT-critical outbound loading first.",
  "priority": "high",
  "enabled": true
}

Rules are intent, not code. They are never executed directly — they are handed to the AI interpreter as instructions, and the AI's resulting proposal is always re-validated by deterministic code. A malformed or contradictory rule can, at worst, produce a proposal that the validator rejects; it can never break a constraint or corrupt the baseline.

7. Deterministic Baseline Algorithm

The baseline is computed with zero AI involvement and is always a complete, constraint-valid plan.

INPUT: Graph + live data + operator settings (mode, HC, targets)
OUTPUT: Constraint-valid baseline HC allocation + projected flows + timeline

ALGORITHM:
1. IDENTIFY output node (what defines TPH)
2. WORK BACKWARDS through the graph:
   a. Output node: how much can it produce given WIP state?
   b. WIP pools: growing/draining/steady? Determine mode implications.
   c. Middle nodes: what feed rate does the output need?
   d. Source nodes: what volume is available to feed the pipeline?
3. LOCK mandatory allocations (min HC constraints, fixed crews)
4. SIZE each node's HC based on what downstream needs (top-down)
5. VALIDATE:
   - Every node's capacity >= its input flow (no jams)
   - All hard constraints satisfied
   - HC sums to available flow HC (conservation)
   - WIP trajectory stays within thresholds for the planning horizon
6. IF validation fails: adjust and re-run
7. CALCULATE projected flows, TPH (transient + steady-state), timeline
8. EMIT baseline as the input to the AI interpreter stage (Section 9)

9. The Decision Loop (AI as Interpreter)

The decision loop runs in three deterministic-bounded stages every optimization cycle. The AI participates only in stage 2, and only as a proposer.

9.1 Stage 1 — Deterministic Baseline (code)

Run Section 7. Produce a constraint-valid baseline. If there were no rules and no AI, this is the answer. It is always safe and always producible.

9.2 Stage 2 — Rule Interpretation (AI proposes)

The engine identifies decision points — nodes that (a) carry one or more enabled ai_rules AND (b) are in a genuinely ambiguous state (headcount contention, near a threshold, an edge case the baseline handles poorly). Only these trigger an AI call. Nodes with no rules, or rules that aren't currently relevant, are skipped.

For each decision point, the AI interpreter receives a scoped payload:

{
  "node": { /* the node's live state */ },
  "neighbors": { /* fed_by and feeds nodes' state */ },
  "baseline_allocation": { /* what stage 1 assigned this node */ },
  "wip_context": { /* relevant WIP pool trajectory */ },
  "operator_rules": [ /* this node's enabled ai_rules text */ ],
  "mode": "racecar | boat"
}

The AI returns a proposal only — never applied directly:

{
  "node_id": "jam_break",
  "proposed_hc_delta": 2,
  "source_hint": "ar_induct",
  "rule_id": "rule_jam_recirc",
  "rationale": "Mezz WIP trending toward recirc threshold in ~12 min; rule prioritizes jam break coverage."
}

The AI does no arithmetic. It reads intent + state and expresses a bounded adjustment with a traceable rationale.

9.3 Stage 3 — Validation & Reconciliation (code disposes)

Every proposal is re-checked by the deterministic validator before it can affect output:

  1. Constraint re-validation — does the adjusted allocation still satisfy min/max HC, no-jam capacity, and WIP thresholds? If not, reject the proposal and log it (never silently apply).
  2. Headcount conservation — HC is finite. Adding to one node must subtract from another; that bookkeeping is arithmetic, done by code.
  3. Contention resolution — if multiple accepted proposals compete for the same headcount, resolve using site-scoped rules (Section 6.5) fed into a deterministic priority ordering. Ties broken by explicit priority, then by bottleneck impact.

The output of stage 3 is the final allocation: baseline + validated, reconciled adjustments. It is provably constraint-valid regardless of what the AI proposed.

9.4 Contract Summary

AI proposes, code disposes. The AI never sees a knob it can turn directly. It emits proposals; the deterministic validator is the only thing that can change the plan.

10. Explanation (AI as Narrator)

After the plan is final, a single AI call produces the human-facing narrative over the already-decided allocation. This call makes no decisions.

Input:

{
  "final_allocation": { /* the decided plan */ },
  "baseline_allocation": { /* stage 1, for contrast */ },
  "applied_adjustments": [ /* validated proposals with rule_id + rationale */ ],
  "rejected_adjustments": [ /* proposals the validator rejected + why */ ],
  "wip_projection": { /* trend over next hour */ },
  "trailer_timeline": { /* when each drains, what arrives */ },
  "user_question": "optimize | what if... | free text"
}

Output:

{
  "explanation": "Natural-language summary of the plan and why it differs from baseline",
  "rule_trace": [ /* which operator rule caused which adjustment */ ],
  "phased_adjustments": [ /* when to move people as conditions change */ ],
  "risks": [ /* flagged concerns with time-to-threshold */ ],
  "alternatives": [ /* if the operator wants options */ ]
}

Splitting narration from decision-making means the explanation is always faithful to what actually happened (including why a proposal was rejected), and a failure or slowness in narration never affects the correctness of the plan.

11. User Interface

11.1 Graph Builder (site onboarding)

  • Visual drag-and-drop: create nodes, draw edges, set rates and constraints
  • Author node-scoped and site-scoped operator rules in plain language
  • Save as site graph JSON

11.2 Optimizer Panel (current Hydra Engine, evolved)

  • Operator inputs (HC, targets, mode toggle) and live API refresh
  • One-click optimize
  • Output: allocation table, flow rates, timeline, risk flags
  • Rule trace panel — shows which operator rule drove each adjustment and which proposals were rejected and why
  • Chat for follow-up questions and what-if scenarios

14. Future State

The engine becomes the foundation for:

  • Autonomous rebalancing — detects bottlenecks and proposes moves without being asked (still validated by code)
  • Shift pre-planning — given manifest, produce a full-shift staffing timeline before shift starts
  • VTO/VET optimization — "you can release 4 people at 02:00 without TPH impact"
  • Rule libraries — share proven operator rules across sites; new sites inherit a starter rule set
  • Network-level visibility — regionals see which sites are optimally staffed vs which have slack
  • Training simulator — new AMs input scenarios and see how the engine + rules solve them
